1. EXECUTIVE OVERVIEW
-------------------------------------------------------------------------------
The Embrix AI Agent platform uses a hybrid architecture combining cloud-native 
IDE chat assistance (Antigravity) and a fully offline, self-contained local CLI 
engine (embrix.cli + ChromaDB + Ollama). This document provides an objective 
trade-off analysis of each core component in the architecture.


2. COMPONENT TRADEOFF ANALYSIS
-------------------------------------------------------------------------------

[COMPONENT 1]: LIVE AGENT IN ANTIGRAVITY (Cloud LLM: Gemini 3.6 Flash / Pro)
-------------------------------------------------------------------------------
* Role: Interactive AI coding assistant operating inside the IDE chat interface.

  PROS:
  + Zero-Permission Setup: Inspects schema_snapshot.json in-memory via read-only
    tools (view_file) without triggering IDE terminal security popups.
  + Superior Accuracy & Reasoning: Handles complex SQL joins across 1,013 tables
    with near-zero schema hallucination.
  + Massive Context Window: 1M+ token context window enables deep reasoning over
    entire schema catalogs.
  + Fast Response Time: Cloud infrastructure delivers sub-second inference.
  + Cost Transparency: Automatically tracks input/output tokens and calculates
    estimated USD cost per query.

  CONS:
  - Requires Internet Connection: Cannot function without cloud connectivity.
  - API Usage & Token Costs: Incurs minor cloud API token consumption per prompt.
  - IDE Dependency: Tied to the active Antigravity/VSCode conversation session.

  BEST USED FOR:
  - Interactive database exploration, complex analytical questions, building
    Power BI semantic models, and instant visual reporting.


[COMPONENT 2]: UNIFIED CLI ENGINE (embrix.cli)
-------------------------------------------------------------------------------
* Role: Terminal-based entry point and programmatic Python backend module.

  PROS:
  + 100% Self-Contained & Portable: Package code (embrix/) runs anywhere Python
    is installed without needing an open IDE.
  + Zero Scratch File Pollution: Executes RAG, EXPLAIN auditing, and data fetching
    strictly in-memory.
  + Automation & Scriptable: Supports command-line flags (--init, --model, --top_k)
    ideal for scheduled jobs and CI/CD pipelines.
  + Automatic Connection Fallback: Seamlessly switches between live PostgreSQL
    execution and offline schema cache modes.

  CONS:
  - Requires Terminal Execution: Must be executed via command line or background
    process.
  - Hardware Dependent: Performance depends on the host machine's local CPU/GPU.

  BEST USED FOR:
  - Batch query processing, system initialization (--init), automated drift sync,
    and headless server/backend API integrations.


[COMPONENT 3]: QWEN3.5 (Local LLM via Ollama)
-------------------------------------------------------------------------------
* Role: Local open-weights Language Model powering offline CLI query generation.

  PROS:
  + 100% Private & Air-Gapped ($0.00 USD): Zero data leaves the local machine;
    no cloud API costs or subscription fees.
  + Offline Autonomy: Generates valid SQL queries even when internet is down.
  + Flexible Parameter Size: 6.6 GB model balances memory usage and capability.

  CONS:
  - Slower Inference: Takes 10-30 seconds per query on standard local hardware
    compared to sub-second cloud LLMs.
  - Lower Complex Reasoning Capacity: Small 7B/8B parameter models occasionally
    struggle with complex multi-table joins without strong few-shot prompting.
  - RAM/VRAM Resource Footprint: Requires dedicated system memory to run locally.

  BEST USED FOR:
  - Enterprise private database queries, strict privacy compliance, offline desktop
    use, and zero-cost local CLI execution.


[COMPONENT 4]: NOMIC-EMBED-TEXT (Local Vector Embedding Model)
-------------------------------------------------------------------------------
* Role: High-dimensional text-to-vector embedding model running in local Ollama.

  PROS:
  + Small Footprint: Lightweight 274 MB model size with rapid embedding generation.
  + Domain Optimized: Specially trained for semantic search and RAG retrieval.
  + Multilingual & Code Capable: Maps technical column names and natural language
    questions accurately into vector space.

  CONS:
  - Requires Ollama Service: Ollama background process must be active.
  - Fixed Context Window: Optimized for short-to-medium text chunks (table docs).

  BEST USED FOR:
  - Vectorizing table descriptions and converting user questions into 768-dim
    search vectors.


[COMPONENT 5]: CHROMADB (Local Vector Database)
-------------------------------------------------------------------------------
* Role: Persistent local vector store managing schema indexing and 1-hop FK RAG.

  PROS:
  + Embedded & Lightweight: File-based vector database (chroma_db/) with zero
    external server infrastructure required.
  + High Efficiency RAG: Filters 1,013 database tables down to 3-5 targeted
    tables in milliseconds.
  + Integrated FK Expansion: Automatically appends 1-hop Foreign Key linked tables
    to complete relational join paths.

  CONS:
  - Index Maintenance Required: Must be updated (`python -m embrix.cli --init` or
    `drift_sync`) when the live PostgreSQL database schema changes.
  - Local File Storage: Stores index files locally on disk.

  BEST USED FOR:
  - Scalable schema retrieval, preventing prompt bloat, and accelerating local RAG.
